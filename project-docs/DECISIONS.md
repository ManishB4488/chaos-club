| D-026 | Scoring | Scoring rules for all five games in SCORING_RULES.md are approved, including all six open decisions as proposed (2 player Most Likely To allows voting for yourself; 2 player Roast uses 1 to 3 stars; round counts and timers; Impostor has one round per player; a game ends early if too few players stay connected for 60 seconds; Roast blocks slurs, sexual content, threats and personal information but allows mild teasing). Approved by owner delegation; revisit after playtesting. |
| D-027 | Content | The 110 Who's Most Likely To questions (content/en/most-likely-to.json) are approved as drafted, by owner delegation. |
| D-028 | Game engine | Each game is a server module with a common interface (actions in, private views out, timers moved along by a server tick of 4 times a second). Which games can be started is decided by which game modules exist, not by a setting. The question file is read from `content/en/` when the server starts; loading content through the database and admin panel comes later. The testing setting AVAILABLE_GAMES is removed. |
| D-029 | Impostor design | Nobody is told their role. Every player is shown only their own word, and most players share one word while one player holds a related word (Undercover style). The impostor and the crew word are revealed after the vote. If a caught impostor was caught, they get one guess at the crew's word. A round has these steps: read word (10 s), one clue each (30 s each, one word, may not contain your own word), discussion (45 s, or sooner if everyone taps ready), secret vote (20 s), guess (20 s, only if caught), result (10 s). Points are as in SCORING_RULES.md. |
| D-030 | Impostor words | The 100 word pairs in content/en/impostor-words.json are approved as drafted, by owner delegation. |
| D-031 | Moderation | A starter word filter (whole words only) is used for clues and guesses. Its list is short and MUST be replaced or extended with a maintained list and reviewed before the site goes public. |
| D-032 | One program for production | In production the website and the game server run as ONE Node program on ONE address (`server/src/combined.ts`, built with `npm run build:prod`, started with `npm run start:prod`). This is the documented Next.js custom-server pattern with Socket.IO sharing the same HTTP server. It cannot run on Vercel (serverless). Development keeps the two separate programs. In production the browser connects to the page's own address. This resolves D-023: `tsx` stays and becomes a runtime dependency. |
| D-033 | Hosting | Deployed by the owner on Render (free tier) as one program (D-032). Known limits of the free tier: the service sleeps after about 15 minutes without traffic and takes about a minute to wake; it can restart at any time, which ends games in progress. A paid always-on instance removes this. Vercel is not used because the game needs a program that stays running. |
| D-034 | Roast Your Friends | Prompts (content/en/roast-prompts.json, 110) approved by owner delegation. Prompts about a player use the placeholder {name}, filled with a player's nickname, taking turns. Scoring as in SCORING_RULES.md: 3 or 4 players pick the funniest answer (+2 per vote, +1 to the answer with the most votes, shared on a tie); 2 players rate the other's answer 1 to 3 stars. Answers are anonymous until the reveal and screened by the starter word filter. Players can report an answer; reports are kept in memory for review (admin panel later). |
| D-035 | Impostor mode (supersedes D-009 and D-029) | On the owner's explicit requirement: the crew receive the secret word, and the impostor is told they are the impostor and receives NO word. The earlier related-word mode (impostor gets a similar word, nobody told their role) is dropped. The second word of each pair in impostor-words.json is no longer used. |
| D-036 | Private secret delivery (security requirement) | Secrets (a player's role and word) are never part of any room update or broadcast, never logged, and never stored in the browser. A player gets their own secret only as the direct reply to their own request (`game:secret`). The server decides WHO is asking from the connection itself (never from the request), and re-checks room membership and the round step on EVERY request, so refreshes, reconnects and stale connections never reuse an old answer. The browser keeps the secret only in the memory of the component that asked; Hide and Pass clears it, as does the page going to the background, a 15 second timer and every change of step. The crew word becomes public to everyone only in the round result, after the votes and the impostor's guess are final. This feature is NOT complete until the automated checks and the owner's manual browser checks pass. |
| D-037 | The Fake Answer | The 112 trivia questions (content/en/fake-answer-trivia.json) are approved by owner delegation; the owner should check the ANSWERS for accuracy. Scoring as in SCORING_RULES.md, with ONE change: a fake answer that matches the real answer is NOT refused (the earlier plan). Refusing would let a player find the real answer by trying guesses, so such a fake is quietly set aside and the writer is not told. Identical fakes are merged and every writer is credited. A player never sees their own fake among the options. Reports on fake answers are kept for review like Roast reports. |

## Proposed: awaiting owner approval

| ID | Proposal | Why |

| P-11 | Room protocol (server-authoritative). Client to server: `room:create`, `room:join`, `room:rejoin`, `room:leave`, `room:kick`, `room:selectGame`, `room:start`. Each uses a Socket.IO acknowledgement that returns `{ ok: true, ... }` or `{ ok: false, error }`. Server to client: `room:state` (a sanitized snapshot built separately for each player) and `room:kicked` (sent only to a removed player). Who is acting is taken from the socket they are connected with, never from ids the browser sends. A socket can be in only one room. If a player's chosen color is taken, the server assigns a free one. At most 1,000 rooms exist at once. Starting a game is refused for games that are not yet available. On create or join the server issues a random session token that only that player receives; it is kept in `sessionStorage` for reconnecting. Room codes use `crypto.randomInt` over the shared alphabet and retry on collision. Nicknames are unique per room, case-insensitively. If the host leaves, the longest-present connected player becomes host. In the lobby a disconnected player stays listed as disconnected for 60 seconds, then is removed. Rooms with nobody connected are deleted after 10 minutes. Every socket event is validated with the shared Zod schemas and rate limited. | Gives the website and server one clear contract before the lobby is built. |
| P-12 | Socket layer limits: each connection may send a burst of 30 events then 10 per second; create, join and rejoin are further limited to a burst of 5 then one per 2 seconds per connection, and a burst of 20 then one per 2 seconds per visitor address (to slow down room-code guessing). Messages over 10 KB are rejected (raised when drawing is added). `WEB_ORIGIN` may list several comma-separated website addresses (needed to test from a phone). `TRUST_PROXY` is false by default and must be set to true only behind a trusted proxy such as Railway, otherwise every visitor looks like the same address. | Protects the server from abuse before any screen exists. |
| P-13 | Website room client: one shared socket and one small store outside React (`roomClient`), read with `useSyncExternalStore`. Leaving a room page closes the connection, and the seat is kept on the server for 60 seconds so a refresh or Back button can reconnect. Rejoining with the same token from the same connection is a harmless success. The room page reads its code inside Suspense (Cache Components rule). Phone testing needs no setting: the page connects to port 4000 on whatever address it was opened from. | Keeps connection logic testable and avoids React timing bugs. |
